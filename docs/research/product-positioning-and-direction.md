## 2. 市场对标：卡在两个成熟品类的缝里

### 品类 A：dotfile 管理器（成熟，但「工具无关」得不是地方）

`chezmoi` 是最接近的参照——Go 单文件、模板化、密钥管理器集成、多机。`stow`
是符号链接农场，`yadm` 是 `$HOME` 上套 git。

它们把**文件按规则铺到位**，但不理解 `CLAUDE.md` 与 `AGENTS.md` 语义不可互换，
也不会指出「这个项目两个文件并存，而 Codex 配了 fallback，它们在互相遮蔽」。

**「为什么不用 chezmoi 加几个模板」是必须能回答的问题**，答案是领域判断不是模板
引擎能表达的——但这个答案目前没有出现在 README 的前 30 秒。

### 品类 B：平台原生分发（懂语义，但单厂商）

各家自己的 plugin / marketplace 与 MCP 生态，对自己那一端理解最深。

**结构性判断**：平台方会持续吃掉「分发」，但**不会**帮用户把资产装进竞品——
没有动机。因此长期可防守的不是分发，是**多工具编译 + 安全应用**。

### 结论

```text
        懂语义
          ↑
  平台原生 │   单厂商
          │  ★ aiah（多工具 ∧ 懂语义）
  chezmoi │   工具无关
        不懂语义
```

这一格确实是空的，判断没错。问题是**今天有多少人站在这一格里**。

## 3. 它真正解决的问题（按痛感分强弱）

### 痛感强

1. **一份资产要在多个工具里各活一份，格式与落点不同。**
   目前没有替代方案；手工维护必然漂移，且漂移不会立即被发现。
2. **「我改这个配置会不会把工作环境搞坏。」**
   `~/.claude.json` 坏掉等于当场失去工作环境。`diff → apply → doctor →
   rollback` 这条链同类工具基本没有，而破坏后果又特别即时。
3. **「我要分享这份配置，里面有没有 token。」**
   `sensitivity` + `${ENV:}` 引用 + `suspected_secret`。在 AI 配置里放 key 是
   高频事故；到团队场景会直接变成硬需求。
4. **「这台机器上到底装了什么、漂了没有。」** `scan` + `doctor`，纯只读。

### 痛感弱（承认它弱）

5. **跨设备搬运**——多数人 1–2 台机器，`cp -r` 即可。
6. **不可变版本化包**——个人自用属过度设计，价值要到多人场景才兑现。

**当前错位**：README 把最弱的第 5 条当主打，把最强的第 2 条放在后面。

## 4. 「用户小众」怎么办

### 先纠正前提：小众的是**现在这个说法**，不是这套能力

现有定位要求「资产多 ∧ 多设备 ∧ 在乎审计」三者交集，当然小。同一套机器
（profile / 不可变包 / 审计 / 安全应用）换个说法就不小众。

### 三条路

**路线 A：接受小众，做深不做大。**
自用 + 少量同好，按需维护。**这是完全正当的完整结果**，成本最低，且已经处在
这个状态。选它就停止增长焦虑。

**路线 B：降低门槛，把小众做透。**
核心洞察：**`aiah scan` 是被浪费的增长入口**——它只读、不写盘、不执行 hook，
可以这样说：「跑一条命令，看看你机器上积了多少 AI 资产。不装任何东西，不改任何
文件。」零承诺、零风险、有即时反馈（本机实测 29 个候选 / 4 条 findings，多数人
不知道自己攒了这么多）。

**先让人看到问题，再谈解决方案**；当前 README 是反过来的。

**路线 C：换靶子——团队 AI 编码规范落地。★ 推荐**

每个正在导入 AI 编码工具的团队都会撞上同一个问题：

> 我们的审查 skill、编码规范、MCP 配置，怎么让全组人都用上、能更新、还知道谁
> 装了哪一版？

这个需求**不小众且在增长**，现有答案（发内网链接自己拷 / 写进 onboarding 文档）
都很差。而 aiah 已有约 80% 的机器：profile 分层、不可变包与通道、`diff` 人审 +
`rollback`（不强推、不破坏个人环境）、secret 引用、MCP 只读可观测。

缺口只有「谁装了哪版」的审计回收，而
[形态评估 §3.4](product-form-and-distribution-assessment.md) 已论证：那不需要
自研服务端，内网 Git + CI + 一个薄 receiver 就够。

**且 C 与 A/B 不冲突**：个人版是团队版的单人退化形态，代码一份。

## 5.1 P1「macOS 支持」的范围与验证方式（2026-08-02 定）

所有者已就 D9 拍板：**自用与对外都要满足**，并同意支持 macOS，初步范围定为
macOS + Linux。以下是把这个范围落成可执行判据后的结论。

### 好消息：这主要是验证问题，不是移植问题

生产代码里**零 OS 分支**（`rg "darwin|runtime.GOOS"` 在非测试代码零命中），
整套实现统一 POSIX；harness 根 `~/.claude` / `~/.codex` / `~/.grok` / `~/.agents`
在 macOS 同名。因此工作量集中在「证明行为正确」，而不是写新代码路径。

### 分两档，而不是笼统说「支持 macOS + Linux」

| 档位 | 平台 | 依据 |
|---|---|---|
| **完整支持** | `linux/amd64`、`darwin/arm64` | CI 真机跑完整测试 + 假 HOME 闭环 + `install.sh` |
| **交叉编译 + 冒烟** | `darwin/amd64` | 编译 + 版本自检；OS 语义与 arm64 同源 |
| **暂不宣称** | `linux/arm64`、Windows | Windows 的 chmod / shebang / 配置根语义需单独验收 |

分档的依据是一个实质区分：

- **OS 差异是语义的**（file mode、软链、配置根、TTY、`pass` 是否存在）→ 必须真机
  行为验证；
- **arch 差异只是代码生成**（纯 Go + `CGO_ENABLED=0`）→ 交叉编译 + 冒烟即可诚实
  声称。

这让范围可以便宜地扩，而不必为每个 arch 重做一遍完整验收。

### 验证方式：CI 加 macOS runner

当前 CI 全部是 `ubuntu-latest`，`build-matrix` 自己的注释已经写明它「仅证明能编译，
从不证明行为在那里被验证过」（ADR-0003 §4）。这正是 README 目前只敢声称
Linux amd64 的原因。

GitHub 提供 macOS runner（`macos-latest` 即 Apple Silicon），公共仓库免费。
加一个 job 跑现有全套 + 假 HOME 闭环 + `install.sh`，即构成真机行为验证，且
**每个 PR 都重跑，不会随时间腐化**——优于人工验一次。所有者若有 Mac，可再叠
人工 dogfood，但不是前提。

### macOS 特有的待验清单

1. **大小写不敏感文件系统**（默认）：`CLAUDE.md` 与 `claude.md` 是同一文件。
   `mapRulesFile` 已用 `ToLower` 匹配，但 **shadowing 检测在该文件系统上的行为
   必须实测**，不能假设。
2. **`pass` 在 macOS 罕见**（常态是 Keychain），secret provider 覆盖会打折。
3. **Gatekeeper / quarantine**：`curl | sh` 路径不打 quarantine，正常；**浏览器
   从 Releases 页下载会被拦**。彻底解决需 Apple Developer 账号（约 $99/年）做
   签名与公证——**建议先不买，把限制写进文档**，给一行 `xattr -d` 即可。
4. 文件 mode、原子 rename、shebang hooks —— macOS 均支持，但要跑过才算数。

### 构建仍然全部在 GitHub 上

`release.yml` 已经是 tag 触发 → 测试 → 构建 → 发布，零本地参与。加 macOS 只需把
`scripts/release-build.sh` 中写死的 `GOOS=linux GOARCH=amd64` 改回多平台循环。

**一个会影响架构的前瞻点**：若日后实现 **macOS Keychain secret provider**
（`security.md` §2 已列入规划，且 macOS 上它比 `pass` 常见得多），大概率需要
CGO，**必须在 macOS runner 上原生构建**，交叉编译做不到。因此加 macOS runner
不只服务于验证，它同时是该能力的前置基础设施。

### 探针结果（2026-08-02 实跑）

第 1 步已执行：CI 加 `macos-latest`（实为 `macos-26-arm64`，Apple Silicon）跑现有
全套。结论是**工作量落在「半天」这一端**。

| 检查 | 结果 |
|---|---|
| 假 HOME 闭环（build→apply→scan→rollback） | ✅ **首次即过** |
| 安装器回归 | ✅ **首次即过** |
| `go vet` / gofmt | ✅ |
| `go test ./...` | 13 失败 / 17 包中 4 个 |

**零生产代码改动。** 13 个失败全是测试里的路径拼写假设，两个根因：

1. **`/private` 前缀（12 个）**：macOS 上 `/var` 是指向 `/private/var` 的软链。
   生产代码规范化路径是**刻意的安全机制**——解析正是捕获软链逃逸的手段。决定性
   证据是 `PrepareRoot` 返回的 `true` 与 `nil` 完全一致，只有路径字符串不同：
   安全判定本身没问题。修法是给测试加 `canonicalTempDir`，只改那 13 个测试用到
   的 10 处，没动其余 147 处 `t.TempDir()`。
2. **XDG（1 个）**：`os.UserConfigDir()` 在 macOS 返回
   `~/Library/Application Support`，不认 `XDG_CONFIG_HOME`。遵循平台约定才是想要
   的行为，因此改测试而非生产；为 macOS 特判 XDG 是没人要求的产品口味。

**行为层首次即过**是最重要的信号：写入语义、文件 mode、原子替换、软链拒绝在
macOS 上本来就是对的，macOS 支持确实是验证问题而非移植问题。

两个过程教训值得留下：**探针不能停在第一个失败**（初版 `go test` 一挂，闭环与
安装器全被跳过，而那两项才决定工作量）；**按 commit SHA 锁定 run**，否则 push
后立刻轮询「最新 run」会读到上一次的结果。

### 执行顺序

1. **CI 加 macOS runner，先跑现有全套**——这一步是探针，决定后续是半天还是三天；
   在跑出结果前不预估，也不猜；
2. 按暴露的问题修；
3. `release-build.sh` 恢复多平台产出；
4. `install.sh` 放开 darwin，`uname -m` 映射 `arm64` / `x86_64`；
5. 文档平台声明按上表分档改写；
6. 发版验收。

## 6. 明确不建议

- ❌ 再加 TUI 界面——已占生产码约 39%，且增速高于内核；
- ❌ 补 doctor / compose / channel 的 report schema——本仓库并无「每个 report
  都要 schema」的惯例，它补的是一致性洁癖，不解决任何真实路径；
- ❌ 自建服务端——[形态评估 §2](product-form-and-distribution-assessment.md)
  的结论仍然成立；
- ❌ 网盘同步——见 [ADR-0007 §6.1](../decisions/0007-immutable-channel-distribution.md)：
  「把包放已挂载目录」今天就能用；内置网盘客户端会与密钥原则冲突；工作区实时
  双向同步会拆掉不可变包模型的存在理由。

## 7. 一个需要所有者拍板的前提

以上全部建立在「目标是让别人用」这个假设上。

**如果目标就是自用加练手，那当前状态已经是一个完整的好结果**，第 1–5 项都不必做。

若目标确实是外部用户，那当前瓶颈**一行代码都不是**：装不上（macOS）、看不懂在
解决什么（pitch）、没人知道它存在（分发）。这三件事没有一件需要写 Go。
