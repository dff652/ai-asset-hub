# 跨设备迁移与受控版本对齐方案

- 状态：Accepted，迁移底层闭环与 TUI E3.1–E3.4 已随 `v0.1.7` 发布并验收
- 日期：2026-07-30
- 关联：[ADR-0007](../decisions/0007-immutable-channel-distribution.md)、
  [ADR-0008](../decisions/0008-interactive-bootstrap.md)、
  [TUI 产品体验 V2](tui-product-experience-v2.md)

## 1. 产品定位

aiah 是**面向多 AI 工具与多设备的 AI 编程资产管理器**。资产管理是产品类别，
跨工具整合、换机迁移、版本分发、安装检查和撤销是资产生命周期能力。

对外一句话：

> 把 Claude、Codex、Grok 等工具中的 AI 编程资产整理成可版本管理的统一资产库，
> 并安全地迁移到新工具或新设备。

## 2. 三个不同场景

| 场景 | 目的 | 当前支持 |
|---|---|---|
| 跨工具整合 | 把多个工具目录的资产纳入统一事实源 | 已支持 |
| 换机迁移 | 在新设备重建选定工具的受管安装 | 连续发布/取回、资产库前置检查和选定发布包→目标检查→diff/apply 已随 `v0.1.7` 发布 |
| 受控版本对齐 | 比较本机、资产库、通道和当前安装版本，由用户决定发布或取回 | TUI 状态、显式发布和版本选择/取回已实现 |

“实时双向同步”不属于当前能力：aiah 没有后台服务、远端账户、冲突合并、删除传播或
可编辑工作树传输。文案必须说清楚“发布哪个版本、从哪里取回、将应用到哪些目标”。

## 3. 当前可执行的换机流程

完整迁移包含两条相互独立的链路：

1. **可编辑资产库迁移**：用户通过私有 Git、NAS 快照或移动介质迁移资产库。
   aiah 不接管网络传输，也不能从安装包反向重建资产库。
2. **目标安装迁移**：旧设备 build/publish，新设备 versions/pull/diff/apply；
   `bootstrap` 可编排 pull 和强制交互预览。

```text
旧设备资产库
  → 换机前置检查
  → validate/build
  → publish 到普通目录通道
  → 用户用 Git/NAS/U 盘搬运
  → 新设备 versions/pull
  → 自动检查刚取回的确切发布包与目标设备
  → diff
  → typed apply
  → doctor
  → 必要时 rollback
```

device scope、凭据、session、cache 和厂商运行时状态默认不迁移。secret 只以引用进入
资产，真实值必须在新设备 apply 时由环境或 secret provider 提供。

## 4. E3：迁移与版本对齐 TUI

任务首页新增“迁移到其他设备”，内部复用现有 Core：

```text
选择资产库与资产组合
→ 生成不可变版本
→ 选择本地分发通道
→ 发布并显示校验摘要
→ 在新设备查看/取回版本
→ 检查设备差异与缺失 secret
→ 变更预览
→ 确认应用
→ 安装检查
```

统一状态至少显示：

- 资产库版本；
- 当前安装的包版本和目标工具；
- 通道中的最近发布版本；
- 本机是相同、可发布、可取回、存在分叉，还是无法比较；
- device-private 排除项、缺失 secret 和 adapter 降级。

E3 只增加 TUI 编排和状态解释，不实现 Git/rsync/WebDAV 客户端，不自动选最新版，
不把 pull 与 apply 合成未经审阅的一步。

### 4.1 E3.3 换机前置检查的语义

E3.3 在迁移状态页增加 `e 换机检查`：

1. 用户明确选择当前资产库中的资产组合；
2. Core 在内存中复用 build 的 profile 解析，不生成安装包、不创建 `dist/`；
3. 复用 inventory 分类，逐项列出 credential、session、cache、device-state 等
   `device-private` 内容，并明确说明这些内容不会迁移；
4. 复用 adapter 编译报告，显示目标是否支持、将生成多少文件、哪些资产会被丢弃，
   以及哪些资产会降级安装；
5. 对 MCP 模板中的 `${ENV:...}` / `${secret:...}` 只检查本机 provider
   可用性，报告只含 provider、引用名、影响目标和布尔状态，不含解析值；
6. 所有检查项都可在 TUI 中导航查看；`r` 只读重查，`Esc` 返回版本对齐页。

结果分为三类：

- `device-private` 是**按设计排除**，只提示，不阻止迁移；
- adapter `degraded` 是**需确认的能力变化**，不自动阻止；
- 缺失 secret、不支持的目标和 adapter `dropped` 是**阻止项**，页面显示“需处理”。

这里的“可用/缺失”只描述**运行检查的当前设备**。源设备与目标设备应分别检查。
本检查绑定当前资产库与所选 profile，不声称对应通道中任意一个历史发布坐标。
E3.3 没有新增公开 CLI/MCP 工具、网络传输或自动 apply。

### 4.2 E3.4 选定发布包与目标设备检查

E3.4 把目标设备检查绑定到用户实际选择并取回的发布坐标，而不是再次读取新设备上
可能不同步的资产库：

1. `pull` 仍只写用户明确选择的已有输出目录，并校验落地四件套；
2. TUI 使用 pull 返回的 name、version、profile 和 SHA256 调用同一 migration
   Core，重新打开并校验 `.tar`；
3. 报告明确标记来源为 `package`，逐项显示目标支持、adapter 丢弃/降级、
   secret 可用性和本机私有排除项；
4. 坐标或 SHA256 任一不匹配即形成阻止项，不能进入 diff；
5. 选定 SHA256 继续传入 diff/apply Core；包在检查后被替换也会 fail-closed；
6. 检查通过后仍要用户按 Enter 才进入变更预览，再完整输入 `apply` 才写目标目录。

这一阶段同时把通道视为不可信输入：`channel.json` 中每条记录必须使用标准
`packages/<name>/<version>/<profile>` 布局，archive 名、SHA256 和坐标必须自洽且
坐标不可重复；通道目录链中的软链、越界路径、损坏/替换包继续 fail-closed。

“旧版本回退”指用户显式选择旧发布坐标，完成包级检查、diff 和 typed apply；
它不比较版本号大小，也不是静默自动降级。apply 自身的本机恢复点和 typed
`rollback` 仍是另一条故障恢复链路。

## 5. 若未来提供“同步”，必须先补齐

只有具备以下契约后，才能把功能命名为“同步”：

- 明确方向：源端 → 资产库、资产库 → 通道，或通道 → 本机；
- 基于内容哈希或父版本检测分叉；
- 显式冲突状态和人工选择，不做最后写入者获胜；
- 删除使用可审计 tombstone，不静默传播；
- 支持中断恢复、幂等重试、版本历史和恢复验证；
- secret 与 device-private 资产始终排除；
- 所有写入仍有 diff、typed confirmation 和审计记录。

在这些条件完成前，用户界面采用“迁移”“发布版本”“取回版本”“版本对齐”，不使用
“自动同步”或“双向同步”。

## 6. 后续开发顺序

1. E2 应用成功摘要和正式安装包 dogfood 已随 `v0.1.5` 完成。✅
2. E3.1：TUI 只读展示本机安装版本、资产库版本和通道版本。✅
3. E3.2：接入 publish/versions/pull，并保留 pull 与 apply 的审阅边界。✅
4. E3.3：新增换机检查清单、secret/device scope/adapter 兼容性摘要。✅
5. E3.4：绑定选定发布包，完成双设备、失败恢复、旧版本回退和恶意通道夹具验收。✅
6. 根据真实多设备使用数据，再决定是否设计更高层的受控同步协议。

E3.1 于 2026-07-30 完成隔离 TTY 候选与 `v0.1.5` 首次正式安装包验收，并随
`v0.1.6` 复验：未选择通道时正确显示未安装/未选择，读取已有通道后显示最近发布
版本、profile、SHA256 和“与资产库版本一致”；全过程未调用 publish、pull 或 apply。

E3.2 的实现继续复用同一 Core，不 shell out：

- 发布端必须明确选择已有目录作为通道和资产组合，build 成功后显示包路径与通道，
  完整输入 `publish` 才调用不可变发布；空目录在这一步初始化索引与包布局；
- 取回端列出全部 `(name, version, profile)`，光标默认落到最后发布项但不会自动
  取回；用户按 Enter 明确选择并输入已有输出目录；
- E3.2 基线中 pull 后进入既有 Phase C diff；E3.4 在两者之间新增绑定所选发布包的
  只读目标设备检查；只有检查通过、用户进入 diff 并完整输入 `apply` 才写目标目录；
- pull 不覆盖输出目录中的同名产物：完整同内容四件套幂等，残缺或内容不同整单
  fail-closed，失败清理不删除预先存在的文件；
- 本阶段不创建通道目录、不联网、不搬运 Git/NAS/U 盘中的字节。

E3.3 的实现沿用同一 Core 边界：

- 新增只读 `build.Prepare`，让 build 与换机检查共享 workspace 校验、依赖、profile
  和 target 选择，不在 TUI 复制规则；
- Core 报告完整保留目标、secret、本机排除项和 findings，TUI 用可导航列表展示，
  不因终端高度截断后静默遗漏；
- 单元与 TUI 集成测试对资产库和目标 HOME 做前后快照，并断言检查不会创建
  `dist/`；真实解析值不进入报告；
- E3.4 复用 `pkgload.Open` 与 `migration` 预检报告，不在 TUI 复制包、
  adapter 或 secret 判断；双设备夹具验证显式 v1→v2→v1，通道夹具覆盖索引越界、
  目录软链和中断后树/索引恢复。
