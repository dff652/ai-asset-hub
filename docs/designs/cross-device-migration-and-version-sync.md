# 跨设备迁移与受控版本对齐方案

- 状态：Accepted，迁移底层闭环与 TUI E3.1 只读状态页已实现
- 日期：2026-07-30
- 关联：[ADR-0007](../decisions/0007-immutable-channel-distribution.md)、
  [ADR-0008](../decisions/0008-interactive-bootstrap.md)、
  [TUI 产品体验 V2](tui-product-experience-v2.md)

## 1. 产品定位

aiah 是**面向多 AI 工具与多设备的 AI 编程资产管理器**。资产管理是产品类别，
跨工具整合、换机迁移、版本分发、安装检查和撤销是资产生命周期能力。

对外一句话：

> 把 Claude、Codex、Grok 等工具中的 AI 编程资产整理成可版本管理的统一资产库，
> 并安全地迁移到新工具或新设备。

## 2. 三个不同场景

| 场景 | 目的 | 当前支持 |
|---|---|---|
| 跨工具整合 | 把多个工具目录的资产纳入统一事实源 | 已支持 |
| 换机迁移 | 在新设备重建选定工具的受管安装 | 底层闭环与 TUI 只读状态已支持，连续向导待实现 |
| 受控版本对齐 | 比较本机、资产库、通道和当前安装版本，由用户决定发布或取回 | 只读统一状态已支持，TUI 发布/取回待实现 |

“实时双向同步”不属于当前能力：aiah 没有后台服务、远端账户、冲突合并、删除传播或
可编辑工作树传输。文案必须说清楚“发布哪个版本、从哪里取回、将应用到哪些目标”。

## 3. 当前可执行的换机流程

完整迁移包含两条相互独立的链路：

1. **可编辑资产库迁移**：用户通过私有 Git、NAS 快照或移动介质迁移资产库。
   aiah 不接管网络传输，也不能从安装包反向重建资产库。
2. **目标安装迁移**：旧设备 build/publish，新设备 versions/pull/diff/apply；
   `bootstrap` 可编排 pull 和强制交互预览。

```text
旧设备资产库
  → validate/build
  → publish 到普通目录通道
  → 用户用 Git/NAS/U 盘搬运
  → 新设备 versions/pull
  → 设备与 secret 前置检查
  → diff
  → typed apply
  → doctor
  → 必要时 rollback
```

device scope、凭据、session、cache 和厂商运行时状态默认不迁移。secret 只以引用进入
资产，真实值必须在新设备 apply 时由环境或 secret provider 提供。

## 4. E3：迁移与版本对齐 TUI

任务首页新增“迁移到其他设备”，内部复用现有 Core：

```text
选择资产库与资产组合
→ 生成不可变版本
→ 选择本地分发通道
→ 发布并显示校验摘要
→ 在新设备查看/取回版本
→ 检查设备差异与缺失 secret
→ 变更预览
→ 确认应用
→ 安装检查
```

统一状态至少显示：

- 资产库版本；
- 当前安装的包版本和目标工具；
- 通道中的最近发布版本；
- 本机是相同、可发布、可取回、存在分叉，还是无法比较；
- device-private 排除项、缺失 secret 和 adapter 降级。

E3 只增加 TUI 编排和状态解释，不实现 Git/rsync/WebDAV 客户端，不自动选最新版，
不把 pull 与 apply 合成未经审阅的一步。

## 5. 若未来提供“同步”，必须先补齐

只有具备以下契约后，才能把功能命名为“同步”：

- 明确方向：源端 → 资产库、资产库 → 通道，或通道 → 本机；
- 基于内容哈希或父版本检测分叉；
- 显式冲突状态和人工选择，不做最后写入者获胜；
- 删除使用可审计 tombstone，不静默传播；
- 支持中断恢复、幂等重试、版本历史和恢复验证；
- secret 与 device-private 资产始终排除；
- 所有写入仍有 diff、typed confirmation 和审计记录。

在这些条件完成前，用户界面采用“迁移”“发布版本”“取回版本”“版本对齐”，不使用
“自动同步”或“双向同步”。

## 6. 后续开发顺序

1. E2 应用成功摘要和正式安装包 dogfood 已随 `v0.1.5` 完成。✅
2. E3.1：TUI 只读展示本机安装版本、资产库版本和通道版本。✅
3. E3.2：接入 publish/versions/pull，并保留 pull 与 apply 的审阅边界。
4. E3.3：新增换机检查清单、secret/device scope/adapter 兼容性摘要。
5. E3.4：完成双设备、失败恢复、旧版本回退和恶意通道夹具验收。
6. 根据真实多设备使用数据，再决定是否设计更高层的受控同步协议。

E3.1 于 2026-07-30 完成隔离 TTY 候选与 `v0.1.5` 正式安装包验收：未选择通道时
正确显示未安装/未选择，读取已有通道后显示最近发布的版本、profile、SHA256 和
“与资产库版本一致”；全过程未调用 publish、pull 或 apply。
