## 3. v0.1.8 → v0.1.9 严格升级

先把正式 v0.1.8 二进制
`2a38529ac38580fc3fd38b6bb9f1b3abd3380b2e26576e46981036e24ebb2636`
放入隔离安装目录，再由它实际执行 `update --check --output json`。返回内容为
`update-available`，并且 `upgradeCommand` 逐字等于：

```bash
curl -fsSL https://raw.githubusercontent.com/dff652/ai-asset-hub/v0.1.9/scripts/install.sh | AIAH_VERSION=0.1.9 sh
```

没有执行任意返回字符串；断言相等后使用相同固定 tag/版本/安装目录运行安装器。
升级后版本、commit 与 SHA256 均等于正式 v0.1.9 资产，旧 SHA 与新 SHA 不同，mode
为 `0755`，安装目录没有 stage 或额外文件。再次运行同版本安装显示 already
installed，SHA256 不变、无写入残留。

这证明 staged-pin 契约完整：v0.1.9 tag 内安装器在发布时仍默认 v0.1.8，但旧版
程序生成的显式目标命令能安全到达 v0.1.9；正式验收通过后，本发布后 PR 才把 main
默认 pin 更新为 v0.1.9。

- `<fake-home>/.claude/library` 在写入前拒绝，目录不存在；

- 名为 `neutral-alias` 的软链接解析到 `<fake-home>/.codex` 后，在写入前拒绝，真实
  目标中没有创建 `library`；

三个拒绝案例均返回非零，并报告 `workspace root overlaps a managed tool directory`。
这关闭了 v0.1.8 中“CLI 能建、TUI/compose 不能用”的边界差异。

## 5. 正式 TTY 与 MCP 回归

Linux tmux 真 PTY 分别运行正式包的：

```text
aiah ui --home <fake-home> --project <fake-project>
aiah
```

两者均进入同一“AI 编程资产管理器”任务首页，显示资产库、资产状态、当前安装和六个
任务入口，并能用 `q` 正常退出。显式隔离目录显示“发现 0 项、尚无受管安装”；裸
入口按设计只读扫描当前真实 HOME，未进入写操作。第一次自动脚本仍匹配旧标题且未
创建 fake project，导致验收断言失败；保留首屏证明二进制已正常运行，修正测试夹具
和当前标题后重跑通过，不记为产品回归。

正式包直接 stdio MCP 协议协商为 `2025-06-18`，`tools/list` 恰好返回 7 个工具：

```text
aiah_asset_status
aiah_diff
aiah_doctor
aiah_migration_status
aiah_scan
aiah_validate
aiah_version
```

全部声明 `readOnlyHint=true`，input schema 禁止额外参数；`aiah_asset_status` 返回
`asset-catalog, ok=true`，`aiah_migration_status` 返回
`migration-status, ok=true`。fake HOME 与资产库调用前后逐目录 diff 一致。
全仓 `TestToolCallsWriteNothing` 也已在候选、PR、main 和 tag CI 中覆盖全部 7 个
handler 的 HOME/project/workspace/channel/package 正文与 mode。

本次变化不涉及 TUI 业务编排、MCP handler 或跨设备通道，因此采用真 TTY 首页与
直接协议零写入回归；完整偏好生命周期、七工具业务面和双设备 apply/rollback 闭环
仍引用 [v0.1.7 正式包验收](2026-08-01-v0.1.7-release-acceptance.md)，不伪称本次
重复执行了未受影响的全部流程。
