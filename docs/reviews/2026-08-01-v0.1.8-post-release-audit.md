## 3. P1：`aiah init` 未复用受管目录边界

public `v0.1.8` 实测会接受 `<home>/.claude/library`，并在其中创建 manifest 和
`assets/`。同一位置会被 TUI、compose 和 asset-library manage 的共享 Core 拒绝，
因此出现“CLI 能建、TUI 不能用”，也可能污染 AI 工具真实目录。

边界定义为：资产库不能位于精确的 `.agents`、`.claude`、`.codex`、`.grok` 目录
及其后代；`.claude-workspace` 等普通同名前缀不属于受管目录。修复候选让 `init`
复用同一 Core，并在任何写入前解析现有软链接、检查已知 HOME/project 和精确路径
组件。回归测试覆盖四类目录、HOME/project/外部路径、软链接和安全 sibling。
变异验证分别关闭路径组件防线、把 CLI 的 HOME/project 传错：前者使四个 Core 测试
按预期失败，后者使 CLI 软链别名测试按预期失败；恢复实现后 focused tests 全绿。
随后完整 `./scripts/check-local.sh` 通过环境、许可、Release/installer/README 门禁、
全仓 test/race/vet/gofmt/lint 和 fake-HOME apply/doctor/rollback 闭环。

`v0.1.8` 不会覆盖既有 manifest，缺口不要求重写或撤回已下载二进制；在下一补丁版
发布前，应在 Release 说明标注“只在 `~/ai-assets` 等独立路径运行 init”。

## 4. P1：tag 没有来自 main

发版时的实际远端状态：

| 引用 | 提交 | 状态 |
|---|---|---|
| `origin/main` | `05aadab85046` | 仍是 v0.1.7 发布后收口 |
| `v0.1.8^{}` | `21ef3fc0d753` | 发布提交，只包含于 dev |
| `origin/dev` | `7ffd351dd12a` | tag 加 v0.1.8 默认 pin/文档收口 |

Release API 的 `targetCommitish=main` 不是来源证明。tag 不包含于 `origin/main`，违反
[发版 runbook](../runbooks/release.md)“先提升 main、同一 commit CI 通过后打 tag”的
规则。结果是默认分支 README 和 `main/scripts/install.sh` 仍指向 `v0.1.7`，而 latest
Release 已是 `v0.1.8`；用户执行 main one-liner 仍安装上一版。

`v0.1.7...v0.1.8` 的提交图是 ahead 33 / behind 14，GitHub compare 展示 171 个文件，
与真实 tag 间文件树的 47 个文件不同。Release 中的自动 Full Changelog 因而噪声很大。
runbook 已补“tag 显式指向 `origin/main` SHA + remote contains”门禁；下一补丁版说明
应人工列 scope，不能照抄这条 compare。

## 5. 收口出口

按以下顺序完成，不能把本地候选、远端 CI 和 Release 验收合并成一个状态：

1. ✅ 受管目录测试完成变异验证，完整 `./scripts/check-local.sh` 通过；
2. 修复与本文档经 PR 合入 `dev`；
3. 用受保护 PR 把待发布文件树提升到 `main`，确认 main CI 与候选 tree；
4. 从 `origin/main` 精确 SHA 创建下一补丁 tag，完成线上资产、严格升级、正式 TTY
   与 `init` 正反路径验收；
5. 发布后更新默认 installer pin 和用户文档，再按 runbook 把最终 main 文件树同步回
   dev；
6. 分别报告 tag 祖先、main/dev tree、Release 资产与 dogfood，不能用其中一项替代
   其他项。

本审计不授权 push、PR merge、tag 或 Release；这些远端动作仍需所有者明确确认。
