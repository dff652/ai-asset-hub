## 2. v0.1.6 → v0.1.7 严格升级闭环

在安装目标版之前，从正式 `v0.1.6` 二进制读取 `update --check --output json`。
程序实际生成的 `upgradeCommand` 逐字等于：

```bash
curl -fsSL https://raw.githubusercontent.com/dff652/ai-asset-hub/v0.1.7/scripts/install.sh | AIAH_VERSION=0.1.7 sh
```

这条命令只作精确断言，不对网络返回执行 `eval`；实际升级使用同一固定 URL、显式
版本和隔离安装目录。结果：

| 项目 | 升级前 | 升级后 |
|---|---|---|
| 版本 | `0.1.6` | `0.1.7` |
| commit | `46e6efccc9ba8ee805fde317adeac65f9e063997` | `b6779193c3ace94dfd8376ed6e82214df75ed841` |
| SHA256 | `2535ed343e6e398f88456f9280a1f51717b3f2a7adb1ff6f3e23f789456aef70` | `8ce852230923e51bc9a17600fafe6b0f1c88d10f3a0a18da360ada3e7a9629b8` |

最终 mode 为 `0755`，没有 `.aiah.install.*` stage 残留；第二次安装同一版本返回
already installed，二进制 SHA256 不变。升级后的版本检查返回 `status=current`、
`updateAvailable=false`。这是 `v0.1.6` 修复升级命令后，首次完整的
Release → Release 端到端证明。

## 3. 正式包 TUI 与偏好生命周期

所有操作使用 Release 安装得到的二进制、fake HOME、fake project 和 fake
`XDG_CONFIG_HOME`，未触碰真实 `~/.local/bin/aiah` 或用户配置。真实 tmux PTY
验证：

1. 裸 `aiah` 进入任务首页，首次启动不创建偏好目录或文件；
2. 进入 Preferences，预览 English 和 detailed，输入既有安全资产库路径；
3. 明确保存后目录/文件权限分别为 `0700` / `0600`；
4. 在中文 locale 下重启，仍恢复保存的 English、detailed 和首选路径提示；
5. `--language zh-CN --density standard` 只覆盖当前进程，配置 SHA256 不变；
6. 写入损坏 JSON 后，首页和设置页显示稳定警告，回退安全默认值，损坏文件字节
   不被自动覆盖；
7. 60 列终端仍能显示必要状态和恢复入口。

首选资产库始终只提示和预填；重启后资产库仍是“未选择”，不会因为偏好获得写权限。

## 4. MCP 正式包零写入

直接 stdio JSON-RPC 依次完成 `initialize`、`notifications/initialized`、
`tools/list` 与两个统一状态调用。server 协议为 `2025-06-18`，恰好注册：

```text
aiah_asset_status
aiah_diff
aiah_doctor
aiah_migration_status
aiah_scan
aiah_validate
aiah_version
```

7 个工具都声明 `readOnlyHint=true`、`destructiveHint=false`，input schema 禁止额外
参数。`aiah_asset_status` 返回 `asset-catalog, ok=true`；
`aiah_migration_status` 返回 `migration-status, ok=true`。fake HOME、project、
资产库和通道在调用前后逐路径、类型、mode、软链目标和文件 SHA256 完全一致。

本次只重跑正式包直接协议；源码候选阶段的 Claude/Codex/Grok 客户端矩阵仍以
[MCP 客户端接入 runbook](../runbooks/mcp-client-acceptance.md)记录为准，不把直接
协议验收夸大为三客户端模型调用重跑。

## 5. 双设备业务闭环

正式包在两个 fake HOME/project 间完成：

```text
build → diff → apply → doctor
→ publish → 重复 publish 幂等 → versions → pull
→ 第二设备 diff → apply → doctor
→ 两端 rollback → doctor
```

源包与取回包 SHA256 均为
`4c0556b24564a618c6a838e5bc5c6c857131f108138cfa9e40e54dcd3c490261`。重复发布后
通道树的路径、mode 和文件摘要不变；第二设备 deployment 版本为 `2026.07.1`；
两端 rollback 后 `deployment=null` 且 Doctor `ok=true`。

该结果证明 E3.2–E3.4 的公开 Release 二进制业务闭环；网络传输仍不属于 aiah，
实际设备间复制继续由 Git/NAS/rsync/U 盘负责。
